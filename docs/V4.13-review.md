# RadioClock V4.13 — BT status and daily Wi-Fi access

V4.13 makes the blue GPIO2 LED a BT sync indicator, optionally restores minimal Bluetooth status after reboot, adds a daily Wi-Fi web-access window and updates the overview status colours. It preserves the approved eight-page sidebar and existing time-delivery protocols. This release publishes source only.

Active sketch: `firmware/RadioClock_V4_13/RadioClock_V4_13.ino`. Dependencies remain **Arduino-ESP32 3.3.12**, **NimBLE-Arduino 2.5.1** and **ArduinoJson 6.21.5**. Keep the complete 11-file sketch folder, including all eight headers and `partitions.csv`.

## Approved scope

Before implementation, the user approved changes to LED handling, BT result/history persistence, configuration/API handling, the Wi-Fi power manager and UI rendering. They also approved saving only the first successful sync each Brisbane calendar day and retaining setup AP, startup/recovery access and NTP wakeups outside the new daily Wi-Fi window.

BT packet protocols, optional battery/font transactions, LF generation/timing and working Wi-Fi/AP/NTP connection helpers remain unchanged. Existing saved LED Off choices, Wi-Fi credentials, watch bindings, independent RF/BT timezones and recurring schedules are preserved. The user's README hardware/range details, font-success report and original author credits were retained.

## LED behavior

With **Settings → Enable blue ESP32 BT sync indicator** On, GPIO2 flashes only during an actual BT connection/time-sync transaction, including blocking GATT writes. Passive watch listening, Wi-Fi and LF transmission do not make it flash.

Successful TIME delivery leaves the LED solid for **24 hours from its UTC timestamp**. An actual failed BT transaction clears that indication; no-watch windows and RF-deferred attempts do not clear a previous success. Optional battery/font errors do not negate a successful TIME delivery. A solid indication can continue during LF transmission. Master Off always keeps the LED dark. A restored successful snapshot can resume the indication after reboot once the clock is valid and the saved success is less than 24 hours old.

The existing separate LED task remains; radio envelope timing and the C3 shared RF-envelope pin ownership are unchanged.

## Minimal flash retention

**Watch (BLE) → Last watch result → Save BT sync status to flash** is a saved toggle, default On. It immediately saves the first successful TIME delivery each **Australia/Brisbane calendar day**, independent of the selected BT timezone. Later successes and failures remain in RAM. The user explicitly accepted that reboot restores the first saved daily snapshot and may forget a later RAM-only failure.

The compact binary snapshot contains:

- UTC success timestamps and watch/profile address/protocol identity needed to restore valid delivery/completion evidence.
- Four BT diagnostic counters: connection attempts, acknowledged writes, notifications and response errors.
- Saved-day quota, retention generation, schema/size and CRC validation metadata.

It contains **no event logs, serial output, battery readings, font results or error text**. The native codec fixture measures 168 bytes and enforces a maximum of 192 bytes. Battery/font results remain RAM only. UTC timestamps are formatted for display in the selected BT timezone/offset; profile completion restores only when the current watch binding matches.

Routine successful syncs no longer request a configuration save merely to record history. Frozen legacy history fields prevent current RAM results leaking into unrelated settings saves. Pairing still saves a newly changed watch binding as required configuration.

The history writer seals and validates the bounded snapshot, writes a temporary file, checks the exact readback and atomically renames it. A failed commit preserves the previous snapshot and does not retry during that uptime/day. Boot reads history without writing it. An already committed saved-day quota survives reboot and toggle changes; a backward clock adjustment cannot open a previously saved day. LittleFS may perform internal data/metadata operations when committing the snapshot, so the quota limits successful snapshot commits rather than raw flash operations.

Turning history Off retains current RAM data but disables history writes/restoration across reboot and invalidates the old snapshot for later re-enabling. Saved-day metadata still prevents a second successful commit that day. Toggle changes themselves persist required configuration, without writing or deleting the history file. The separate general failed-configuration background-retry reduction remains queued in `docs/NEXT_VERSION.md`.

The pinned SDK has flash core-dump support enabled. To honor the user's no-flash-logs instruction, the V4.13 partition table removes only its optional 64 KB core-dump partition row. Application and LittleFS addresses/sizes remain unchanged, with the final 64 KB unused. The SDK flag itself is unchanged; there is no core-dump storage partition in this project's image layout. The project validator checks that the table has no core-dump partition.

Review of official IDF 5.5.5 [`core_dump_flash.c`](https://github.com/espressif/esp-idf/blob/v5.5.5/components/espcoredump/src/core_dump_flash.c) and [`core_dump_elf.c`](https://github.com/espressif/esp-idf/blob/v5.5.5/components/espcoredump/src/core_dump_elf.c) confirmed that missing DATA/COREDUMP storage returns before configuration, and panic write initialization rejects the absent/invalid configuration before erase/write. There is no fallback partition address. The boot message **“No core dump partition found!”** is expected when crash storage is omitted; serial panic/backtrace diagnostics remain available.

## Wi-Fi access and status

**Settings → Daily Wi-Fi access** adds start/end times and an independent timezone, default disabled with **18:00–20:00 Australia/Brisbane** selected. Enabling saves automatically and selects Power-save. Start/end/timezone edits save together using the schedule button, with validation and rollback on storage failure.

The daily window includes its start and excludes its end. Overnight windows are supported; equal start/end is rejected. Its timezone conversion handles the existing supported fixed/DST-aware zones without changing RF or BT timezone settings. Always on overrides the daily window; disabling the window leaves the current power mode unchanged. Setup AP, five-minute startup/recovery access, association handling and existing brief NTP wakeups remain available outside it.

The overview Wi-Fi tile is green for a normal station connection and red in setup AP mode, including AP-plus-station operation. The radio tile is green while LF is active and red while idle. Existing status/API evidence supplies these colours.

## Validation

- `bash scripts/test.sh`: **37 Python host cases passed**, plus UI JavaScript handler checks, native captured/malformed BX packet checks and concurrent RF/BLE arbiter stress over **10,000 RF sessions**, with no modeled overlap.
- History tests exercise immediate first-success saves, later RAM-only success/failure, midnight and clock rollback, boot restoration, counters, Off/On generations, durable toggle changes, retained quota, profile/address/protocol replacement isolation, corrupt/truncated/oversized records and storage failures. They verify no runtime history leaks into config saves and no battery/font persistence.
- LED tests exercise the actual extracted task, BT-only flashing, 24-hour UTC boundaries, failure/master Off, millis rollover, RF isolation and saved-Off restoration.
- Wi-Fi tests exercise daily/overnight bounds, independent timezone/DST conversion, recurring access, existing AP/startup/recovery/NTP/Always-on exceptions, strict grouped input validation, durable saves and failure rollback.
- `node scripts/test-ui-browser.cjs`: passed, including new history/window controls, save failures and stale-response handling, status colours and existing schedule/pairing/battery/font/power regressions.
- Compact history codec and actual history integration fixtures passed AddressSanitizer and UndefinedBehaviorSanitizer checks.
- Node32s compile passed using `esp32:esp32:node32s:PartitionScheme=no_ota,FlashFreq=40`: **1,426,872 / 2,097,152 bytes (68%)** program storage; **62,536 / 327,680 bytes (19%)** global RAM, leaving 265,144 bytes. The CLI reports the board's No OTA capacity; the included sketch-local table retains the project's 3 MB application layout.
- Actual dark/light desktop and phone renderings were inspected against `ui/v32_ui_mockup.png`. All eight labelled sidebar routes and the established arrangement remain; no fundamental layout change was made.
- Independent read-only review found no blocking issue. Scope review confirmed unchanged BT packet/RF/AP/NTP helpers; new behavior is limited to the approved LED, status/storage, access policy, API/UI and version changes.

Physical ESP32/watch testing was not performed in the cloud. Host fixtures and browser tests validate the modeled implementation; they cannot verify the onboard LED, real Wi-Fi access or watch transport.
