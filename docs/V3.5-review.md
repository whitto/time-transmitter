## Behavior implemented

- Sync Now queues a safe manual restart, including retries from passive/automatic windows; pairing and active RF receive specific responses. A completed disconnect barrier releases any temporary client quarantine.
- Pair Watch is separate and transactional. Only explicit pairing ignores the existing binding. Name/address/protocol are committed after an acknowledged time write; errors/timeouts preserve the previous binding. Legacy destructive rebind requests are rejected with Pair Watch guidance.
- Always Wait is appended to the persistent configuration, with protocol metadata per watch profile. Older config files remain readable. Passive scanning accepts only the selected bound address and matching protocol, returns after successes/failures, and resumes after RF preemption.
- Settings show paired watch details, Always Wait state, and exact GW-BX5600/module 3578 C/D instructions. Wi-Fi controls share the existing power-mode enum and apply driver sleep accordingly.
- BLE host/client allocations are retained across disconnect and `deinit(false)`. No application disconnect callback deletes a client or its GATT cache. Reuse waits for a subsequent host event after GAP teardown. The cache is refreshed only on a later safe connection.
- GW-BX5600 SP_REQUEST requires and uses Write Without Response; SP_DATA and TIME use Write With Response. Discovery identifies each missing characteristic/property, and command submission is not counted as an ATT acknowledgement.
- Bluetooth watch time is calculated independently from the station clock: the Watch card selects a fixed/DST-aware zone plus an additive BLE-only offset, defaulting to Australia/Brisbane. The main dashboard reports that pending watch time beside the JJY transmitted time, while `stationTime()` and all JJY/LF encoders continue using the existing station timezone/transmission offset.
- Successful Bluetooth writes persist a date/time timestamp for the overview hero, watch card, and quick status. Automatic Bluetooth slots, completion-day tracking, Wi-Fi wake windows, and LF-overlap checks use the Bluetooth timezone/offset; JJY schedule matching continues using the selected station timezone.

## RF/BLE and concurrency review

`RadioBleArbiter` owns the physical radio resources for the entire BLE controller lifetime and RF session. It covers initialization/teardown and every RF envelope slot, including zero/reduced duty. RF demand closes the BLE initialization gate; the controller remains owned by BLE until its host is stopped and its controller reports IDLE. Failed shutdown keeps RF off with diagnostics.

A 20 ms NimBLE host callout requests safe disconnect/cancel when RF becomes due, allowing a loop task blocked in GATT to unwind. The disconnect callback publishes flags and schedules a later host barrier; that barrier drains the callout before objects/host event storage can be reused. Monitor failures terminate the connection. Controller cleanup also handles NimBLE initialization failures before the host starts. This callout lifecycle was inspected against the pinned classic ESP32 implementation.

RF relinquishes ownership only after a successful zero-duty update, or successful LEDC detach followed by a low GPIO. If both operations fail, it retains ownership and prevents BLE initialization. Same-station startup restores LEDC after detach. The hardware carrier, time-code encoders, wall-clock envelope phase, second-boundary scheduler and NTP confidence model are preserved.

Cross-task request/acknowledgement flags and shared scalar inputs use atomics. Commands consume request flags using `exchange(false)`; refresh/SNTP requests cannot be lost through load-then-clear races. Schedule changes still use the radio pause barrier; pause retry acknowledgements cannot satisfy a later resume request. Status reads coherent schedule snapshots and protected NTP statistics. Scan callbacks publish fixed-size buffers with a generation check and mutex, rather than mutate shared Arduino Strings.

## Checks executed

`bash scripts/test.sh` passes all seven checks:

1. Asset validation: embedded gzip matches editable HTML byte-for-byte; JavaScript parses; 82 DOM IDs are unique; static element references resolve; all 9 UI API paths exist; filename/header/version and 4 MB partition bounds match.
2. UI runtime handlers: Bluetooth zone/offset requests, JJY/BT dashboard preview, delivered date/time rendering, Always Wait/Wi-Fi mapping, failure rollback, stale polling protection, literal watch text, separate repeatable Sync/Pair requests, RF status and replacement watch details.
3. BLE lifecycle C++ harness: correct characteristic properties/write modes, host teardown ordering, retained client/quarantine, reconnect, missing characteristics, response truncation, RF cancellation during connect/GATT, and monitor start/rearm failure.
4. BLE workflow C++ harness: manual retry, stale discovery, explicit pairing success/failure/timeout, profile-specific completion, actual configuration read/write round-trip, Always Wait resumption, RF-deferred windows, failed controller shutdown and partial initialization recovery.
5. RF integration C++ harness: real carrier-silencing/scheduler paths, LEDC failures/detach recovery, lost clock confidence, scheduled/full-time preemption, same-station restore and pause/resume acknowledgement race.
6. Casio BX packet C++ tests: capture-derived 101/28/133-byte responses validate into the official 35/94/133-byte SP_DATA writes, preserve opaque records, and reject malformed/truncated/duplicate/capacity cases. AddressSanitizer and UndefinedBehaviorSanitizer also pass.
7. Concurrent arbiter C++ tests: 512 simultaneous acquisition races and 10,000 RF sessions with modeled physical state; no modeled overlap.

The three Python harness runners each report one executed test containing multiple C++ assertions; these are host mocks, not on-device integration suites. The UI was also checked in Chromium at desktop and 390 px mobile widths with mocked APIs: no horizontal overflow or JavaScript errors, safe literal watch names, and correct checkbox requests.

The final UI is **47,118 bytes raw / 13,227 bytes gzip**. All firmware checks passed; no checks were reported as passing without execution.

## Physical acceptance remaining

1. Flash the included Arduino sketch or matching binaries to a classic Node32 with 4 MB flash. Verify serial startup, trusted SNTP clock and settings persistence after reboot.
2. Pair GW-BX5600/module 3578 with C held for at least three seconds. Confirm the displayed paired name/address/profile and actual watch time. Try a failed replacement, verify the old binding survives, then successfully replace it.
3. Press D once in Timekeeping Mode; test repeated Sync Now, expired/failed attempts, scheduled windows, and Always Wait after success/failure. Verify an unknown watch is ignored without Pair Watch.
4. Measure LF output and controller state during every supported station's scheduled/full-time transmission, including when RF starts during scan, connection and GATT. Verify controller-off logging precedes the first carrier edge, no RF/BLE overlap, and continued second-boundary/envelope alignment.
5. Inject disconnects/missing characteristics and controller shutdown failures. RF must remain off on unconfirmed BLE shutdown; repeated attempts must not panic. Verify Bluetooth returns after RF and Wi-Fi power controls behave as selected.

GATT runs in the foreground loop; HTTP polling may pause during a transaction. The independent radio task and host preemption remain active. The 20 ms check interval is an implementation interval, not a measured disconnect-latency or RF-edge guarantee. Build/host evidence does not establish physical waveform timing, live watch synchronization or absence of all device-level crashes. Other ESP32 variants/custom NimBLE timer configurations need their own compile/lifecycle review.

The build and host checks ran in Codex; no device flash or physical hardware testing was performed. Publishing the repository or compiled artifacts does not establish hardware acceptance. The JJY carrier audit is in `docs/JJY-transmitter-audit.md`; the accessible V2.6 predecessor matches the current GPIO, LEDC, frequency, duty, and envelope settings. An exact V2.7/V2.8 source link would be needed to compare those unavailable revisions.
