# Long-run embedded reliability review — V4.14 build R2

Reviewed on **9 October 2026**. After the original V4.14 R1 review, the user explicitly authorized **all suggested reliability changes in V4.14**. R2 implements those changes; the earlier approval requirement no longer leaves these fixes queued. The user also requires a fresh reliability review after every code change or feature, completed **before publication**. `AGENTS.md` records this continuing requirement.

No steadily growing application RAM leak was demonstrated in the original review. The confirmed failure paths and recovery gaps nevertheless required correction. R2 addresses them without periodic reboot schedules or flash logs. Native/fault tests check production helpers and extracted functions; physical radio, watch, power and network behavior still requires an ESP32 soak.

## Recovery behavior and bounds

Configuration serialization uses one shared 2 KB buffer on loopTask, so a low-memory save cannot silently shorten the record. Schedule documents are limited to 8 KB and 24 entries; an incomplete document never opens a temporary file. Writes are acknowledged as durable only after full write/readback and replacement. Boot configuration admission limits the entire record below 2 KB and physical lines to 64 bytes. A failed configuration commit stops idle retries and leaves the old file intact.

A mount fault never formats automatically. The existing setup AP remains accessible with no RF. Settings offers confirmed erase/restart only in a mount-fault AP; an ordinary save failure cannot authorize erasure. A new board whose filesystem was erased can require this explicit initialization. Firmware uploads should not routinely erase saved settings.

Station association attempts are limited to 30 seconds. AP-plus-station retry preserves setup access; retry backoff starts at 30 seconds and caps at 15 minutes. The independent clock wake starts 60 seconds before the adaptive NTP interval, or immediately for unsynchronized/rejected time; a 120-second wake burst has bounded retry backoff. Startup/recovery web access, optional daily access and LF/BT preparation windows remain. Successful association alone does not establish clock trust or permit an invalid LF frame.

The patched NimBLE library is **2.5.1-radioclock.1**, based on the checksum-verified official 2.5.1 source archive. It includes the upstream [host-timer correction](https://github.com/h2zero/NimBLE-Arduino/commit/e0c8f5a558893197ae60c3606ded01a2dbb88863), checked singleton allocation and initialization failure propagation. Original notices/licenses and a source manifest remain. Ordinary Library Manager 2.5.1 must be replaced; an unpatched library deliberately fails the firmware build. This corrects a dependency defect without proving it caused every historical panic.

BT transactions have a 45-second deadline. Cancellation uses the normal host disconnect/ATT path and preserves callback storage until completion; it never returns early while a stack-local ATT completion object remains referenced. Incomplete teardown retains RF exclusion, retries termination and uses controlled recovery if it cannot unwind. Low-memory admission reduces allocation risk; it cannot prove that every internal SDK allocation will always succeed.

RF progress checks latch a RAM fault and force the GPIO carrier off after missing timer/task progress. Timer recovery is bounded and requires genuine interrupts before output is permitted. An independently unrecoverable radio/application stall can trigger a controlled restart after RF is forced off. These are fault responses, not periodic maintenance reboots. Monitor thresholds and grace periods are tested against bounded BT work; device stack/scheduling margins still require measurement.

Clock confidence uses a conservative absolute drift bound, including uncertainty at both measurement endpoints; signed diagnostic drift cannot cancel that bound. Implausible replies are rejected through the documented SDK pre-commit SNTP hook before `settimeofday`, invalidating trust and requesting a short retry. Initial acquisition remains possible; later replies must be consistent with monotonic holdover. Tests demonstrate the software gate, not authenticated NTP or hardware oscillator accuracy.

## Flash policy preserved

No serial logs, heartbeat/headroom samples, fault history, battery/font results or periodic status records are written to flash. Essential changed configuration and schedules remain durable. Optional BT retention saves only the first successful TIME delivery each Brisbane day immediately; later outcomes stay in RAM. Optional crash dumps remain default Off and permit SDK panic writes only when explicitly enabled, independently of the BT daily quota. Flash filesystems may perform internal metadata writes when committing an authorized record.

## Remaining acceptance and limitations

Run a physical Node32s/GW-BX5600 for days, then weeks, with the exact dependency/ELF build. Capture matching-cycle heap free/minimum/largest block, loop/radio/LED/monitor/NimBLE stack headroom, fault/progress fields and serial output externally or in RAM. Do not add flash logging or scheduled reboots to conceal a fault.

Exercise repeated manual/scheduled time sync with font/battery options, disconnect/cancel/retry, Always Wait, RF priority and controller shutdown/restart. Remove/restore the router, block NTP, exercise daily/overnight access, all-day LF schedules and date/DST/rollover cases. Inject allocation/storage/timer faults separately and confirm old files remain, recovery remains accessible, no idle config-write retries occur and RF stays off when timing/time is untrusted. Confirm the daily BT quota across reboot/toggle and crash storage Off/On on a test board.

No measured steadily growing application leak is claimed, and no cloud test guarantees years without reboot. Residual risks include hardware power/flash/oscillator faults, unexercised SDK paths, real scheduling/stack margins and watch-specific BLE behavior. Historical corrupted backtraces remain unattributed unless decoded against the matching user ELF. Re-run the embedded reliability review after every later change and before publishing.
