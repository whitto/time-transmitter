The reviewed scope is clock reacquisition and drift sampling, Bluetooth shutdown progress and final TIME trust, HTTP request bounds and SSID validation, timer recovery replenishment, strict durable configuration, and checked Wi-Fi shutdown. The user subsequently authorized a newest-four RAM sync list for each selected watch and hours/minutes/seconds uptime in Overview and Diagnostics; those additions received the separate review below. Existing watch packet formats, LF encoder tables, timezones, blue LED/daily-snapshot/crash options and the eight-page sidebar are retained.

Following the user's requested workflow, focused failure regressions and the embedded reliability review happen before publication. The complete suite, browser checks and Node32s compile run against the published source. A failure requires a reviewed, published R2 or later revision before repeating the complete suite.

## Additional approved feature review

`BtRecentSyncs::Store` uses **224 fixed RAM bytes** for four profiles with four outcomes each. Its plain entries and identity arrays allocate no heap and have no callback lifetime. Sync-result recording and HTTP rendering are both owned by `loopTask`. Newest-first indices remain bounded after a million insertions; case-insensitive watch address and protocol matching isolate each binding. Firmware/static schema checks keep profile/protocol counts consistent.

Successful entries use the existing delivered-result UTC epoch. An actual failed transaction records its epoch only while the clock is trusted; otherwise the UI shows **Time unavailable**. Missing-watch windows, passive listening, entry deferrals and RF cancellations do not become failures in the list. An unsuccessful replacement attempt preserves the bound watch's history; a successful changed binding starts a fresh list for that identity. The optional daily flash snapshot and LED success state are unchanged. The ring is never saved or restored, so it is empty after restart even if a daily success snapshot was restored.

The config/status serializer exposes only the selected watch's four rows using the existing checked **8 KB** response buffer and a 24-byte local date buffer. A profile id travels with the rows. The UI merges that pair together and displays it only when it matches the selected profile, preventing a late response from showing another watch's history. It escapes date/protocol text, uses `textContent` for the watch title and replaces at most four DOM rows. The list stays inside the existing Watch result card; all eight navigation items remain. Overview and Diagnostics share the same hours/minutes/seconds formatter, retaining the firmware's 64-bit monotonic uptime source without introducing another timer, request or save.

Focused evidence passed:

- Two ASan/UBSan/leak cases exercise the actual result hook and ring: a million inserts, newest-four order, profile/address/protocol isolation, invalid identities, restart reset, real success/failure, unknown dates, excluded deferrals and safe watch replacement. With history persistence Off, the actual result hook adds no flash writes; replacement queues only the existing required binding save.
- Two actual API cases exercise admitted credentials and the full bounded config/status routes with four history rows, four watch profiles, 24 schedules and escaped strings. The latter repeats **80,000 responses** without retained host allocation growth and returns a clean 503 for overflow instead of partial JSON.
- Three focused VM cases run the shipped list/uptime functions: success/failure ordering, four-row bounds, unknown dates, escaping, unknown protocol, malformed arrays, late selected-profile responses, atomic row/profile merge, restart separation from the daily snapshot, hours beyond 24 and long uptime. The unchanged sidebar/card placement is also checked.

## Cross-cutting review

All nine correction diffs and the additional RAM history/uptime feature have been inspected independently and their focused regressions pass. The independent review caught the unbounded SDK receive-buffer drain, URL/query allocation-completeness gap and handler-side credential copy failure; the final HTTP/credential code closes them. The root integration review caught a legacy SSID/version-marker collision; the final marker and compatibility checks close it. **The reviewed source was cleared before publication**. The complete post-publication tests subsequently passed, as recorded below; the board compile was stopped at the user’s request.

- Clock admission must execute once per reply before `settimeofday`, keep provisional/reacquisition trust false until commit and use monotonic deadlines. Consistent replies confirm agreement; the SNTP callback does not identify independent source servers.
- RF ownership stays closed until the controller is physically confirmed Off. A deadline must not destroy pending callback/client storage; an irrecoverable stalled host requires safe last-resort recovery with RF forced off.
- HTTP limits must apply before body allocation, use one absolute budget across chunks, and reject unsupported body framing rather than permitting an unbounded parser path. The source library installed by Arduino and cloud tooling must be the same reviewed dependency.
- The HTTP route audit is specific to this firmware: JSON replies use fixed lengths and the main page uses fixed-length `send_P`. Both header/body writes reach the same bounded transport. No streaming-file, chunk-response, unknown-length, SSE or upload route is registered. Generic upstream server interfaces do not broaden this sign-off.
- Configuration integrity and field validation must finish before live settings are applied. Corrupt files are retained. Legacy migration is bounded and must add no periodic configuration writes or flash logs.
- Recent sync rows remain a fixed RAM ring, separate from the durable daily snapshot. Repeated outcomes cannot grow storage, alter the existing flash quota or cross watch identities; unknown clock time is not presented as a trusted date.
- Retry replenishment requires continuous qualified timer/task progress over a long healthy interval. A short successful requalification must not reopen an endless retry loop. Lifetime diagnostic counters are independent.
- Wi-Fi desired power state and observed SDK state must remain distinct during failed transitions. Bounded retries stay in RAM and must preserve access/NTP when a connected station cannot shut down.

Focused transcripts and reviewed UI screenshots are retained in [the V4.15 evidence directory](build-evidence/v4.15/). HTTP evidence includes [the five-case fault run](build-evidence/v4.15/pre-publication-http-focused.txt) and [the complete source pin check](build-evidence/v4.15/pre-publication-http-pin.txt). The HTTP library is required alongside the existing patched NimBLE and crash-gate libraries; its unique header/class and validated installer prevent silently compiling the unchanged SDK parser.

## Physical acceptance and limits

Host fault checks, even combined with a successful board compile, cannot establish years of physical reliability. On the Node32s/GW-BX5600, repeat manual/automatic Bluetooth sessions, real scan/controller shutdown, router/NTP outages, scheduled Wi-Fi Off/On, legacy configuration loading/next-save upgrade, interrupted saves and timer faults. Check recent-row success/failure order across profile changes and watch replacement, unknown timestamps on confidence loss, and an empty ring after restart alongside the separately restored daily snapshot. Record free/minimum/largest heap block, task stack minima, real RF boundary timing and restart reasons via RAM, serial or external captures. Do not use periodic flash logs or maintenance reboots.

The checked parser/configuration/credential paths do not make every SDK or application `String` allocation allocation-free or failure-proof. Extreme heap exhaustion, fragmentation and platform task-stack pressure still require hardware acceptance; generic upstream server interfaces and other handler-side String copies are outside this scoped sign-off. No growing application allocation leak is demonstrated by the focused runs.

The existing NTP policy allows trusted holdover. Opening a pre-transmission Wi-Fi window provides an opportunity for synchronization; it does not force a fresh reply before every LF session when the SNTP client is already connected. A new force-before-every-transmission policy was not requested in this correction scope.

The reliability sign-off is limited to inspected source and reproduced paths. The [complete release notes](V4.15-release-notes.md) state the successful post-publication checks and explicit board-compile omission.
