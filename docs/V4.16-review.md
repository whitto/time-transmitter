# V4.16 R1 source reliability review

Date: 10 October 2026 (Australia/Brisbane). Base: published V4.15 R4.

## Authorized scope and validation exception

The user requested: “fix the two issues you found and publish the code as V416, do not perform any additional testing just publish the corrected code.” This authorizes the two schedule fixes and version/publication metadata. The latest request overrides the routine test/compile/browser workflow for this release. Review was by source inspection only; no additional host tests, fault fixtures, sanitizer runs, browser checks or ESP32 compilation were executed. Previous-version evidence must not be represented as V4.16 results.

## Automatic binding and occurrence handling

`bluetoothProfileBindingReady` validates profile/protocol bounds before indexing the binding arrays. `serviceBluetoothSync` skips unpaired/mismatched automatic candidates before stopping any passive window. Invalid slots remain retryable without causing repeated scan-stop/restart operations while Always Wait listens for a valid selected watch.

`startBluetoothWindow` records the automatic occurrence only after profile/protocol binding validation and accepted civil-window duration. The date and remaining duration use the same Bluetooth-local snapshot and the existing midnight/year identity calculation. No attempt marker is consumed by an invalid opening. The existing 11-minute window and signed-difference `millis()` expiry remain.

## BT civil-time settings and durable saves

The generic configuration handler stages and validates both supplied BT time fields before mutating either. Checked argument copies detect allocation failure. Rollback uses a fixed 32-byte stack buffer; supported zone names fit within it. The live timezone String reserves capacity for both the old and candidate names before assignment, so apply and rollback need no further allocation. The temporary candidate is request-scoped; there is no growing store or new global history.

Effective BT time changes are rejected while `btBleBusy` is true. All seven downstream generic save paths share the local commit wrapper, preserving grouped LF/Wi-Fi/BT requests. The wrapper installs candidates only for the checked atomic save, restores the old BT fields on failure, and changes automatic runtime state only after success. A successful edit uses the existing bounded four-slot reset and scan-stop path; the next service pass recomputes eligibility and the window deadline. Same-value saves do not rearm occurrences.

Failed BT-only time saves leave the previous automatic window/deferred/occurrence state intact. Existing manual-selection side effects in combined requests retain their earlier behavior; the change does not promise rollback of every other field in a mixed request.

## Lifetimes, resource use and independence

The commit lambda is synchronous and request-local; its captured buffers/Strings do not escape into callbacks. Scheduling remains on loopTask. Existing scan-stop acknowledgement and retained host/controller ownership protect callback lifetimes and RF exclusion if shutdown is delayed. No callback, task, timer or BLE object allocation is introduced.

Invalid slot checks are bounded array/enum/address checks without flash I/O or scan operations. Rearming touches four RAM entries once per successful effective settings edit. Configuration still uses its existing one checked save; no recurring config writes, history writes or logs are added. Failed saves retain the existing no-background-retry storage fault behavior.

The LF encoder, carrier/envelope timing, RF/BLE arbiter, NTP/Wi-Fi recovery, BLE packet/protocol, font/battery, LED/history and partition/library sources are carried forward from V4.15 R4. UI edits are version labels only, preserving the sidebar/layout. No browser/render test was run under the user's exception.

## Independent review conclusion

A second reviewer inspected the actual implementation and found no blocking regression within these two fixes. Review covered bounds, checked allocation and rollback, grouped saves, scan/callback ownership, rollover/midnight handling and flash-write frequency. This is source review, not runtime acceptance or an ESP32 build result. No test pass is claimed for V4.16.

The reported misses at 12:30/18:30 remain unattributed without device logs. The ESP opens listening windows; it does not enable or program the watch's automatic-adjustment setting. RF overlap, slot/profile selection, actual automatic advertising and cold-start memory admission remain device-side diagnostic questions. The cold-start memory threshold was deliberately retained.
