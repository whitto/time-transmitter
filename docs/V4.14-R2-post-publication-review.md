# V4.14 R2 — post-publication embedded-systems review

Reviewed 9 October 2026 against published commit **a727dd64fabebbbc06a22f3d4644b5d7268c0d05**, immutable tag **v4.14-r2**. This additional review was requested after publication and made no firmware changes. The original approved reliability corrections are present. The complete post-publication regression suite passes; the further fault reproductions below identify conditions that suite did not cover.

## Validation of the published version

- 61 Python unittest cases across 20 groups passed, plus browser/VM checks, captured packet tests and concurrent RF/BLE stress (10,000 RF sessions).
- Actual bounded GET response stress: 20,000 cycles / 80,000 responses under ASan/UBSan, including four profiles, 24 schedules, escaping and overflow. Zero retained host allocation growth is verified; this does not prove allocation-free ESP32 SDK HTTP operation.
- Exact Node32s build: esp32:esp32 3.3.12; 40 MHz / No OTA; included NimBLE 2.5.1-radioclock.1; ArduinoJson 6.21.5; RadioCrashDumpGate 1.0.0.
- Flash: **1,427,796 bytes**. Global RAM: **73,056 bytes**, leaving **254,624 bytes** before runtime allocations/stacks.
- Actual ELF verifies IRAM crash-dump gating and strong pre-commit SNTP dispatch. ELF SHA256: **1ea4a9f8cb1e921f77367b5153c1464f70f4fde01b6bdf9f77f5e00f8ac5456e**.
- Diagnostics uptime renders hours/minutes/seconds, including hours above 24; no counter truncation was introduced.
- All four direct source ZIPs downloaded and matched every tag file byte-for-byte. Arduino archive contains 14 sketch files, the five-file crash library and 478-file pinned NimBLE library; 497 files total. No firmware/library binaries are included.

## Findings needing a further revision

### P1 — correct NTP cannot promptly recover a bad initial time anchor

[Acceptance filter](https://github.com/whitto/time-transmitter/blob/v4.14-r2/firmware/RadioClock_V4_14/RadioClock_V4_14.ino#L2449) accepts the first plausible reply, then compares later replies against that unchanged anchor with a 1,000 ppm maximum correction allowance. An incorrect initial reply one hour ahead was accepted. Actual clock-function reproduction rejected all 5,760 correct replies over the next 24 hours and kept confidence Unsynchronized. The allowance would need roughly 41.6 days to grow enough to accept that correction. Restarting SNTP does not reset the anchor.

Use bounded, consistent multi-reply/server-confirmed reacquisition for large corrections while keeping RF and BT off until confidence is restored. Do not simply accept any large jump. Consider provisional confirmation of the first clock acquisition as well. This is a reproduced software recovery path, not a reported hardware incident.

### P1 — a stalled BLE scanning host can permanently block RF

[Shutdown workflow](https://github.com/whitto/time-transmitter/blob/v4.14-r2/firmware/RadioClock_V4_14/RadioClock_V4_14.ino#L3109) repeatedly retries an unacknowledged scan stop. With no connected client, the client quarantine deadline never starts. Each bounded attempt returns to loop and refreshes its heartbeat, so the loop watchdog cannot detect the lost host progress. A real-workflow/scan-coordinator reproduction made 80 retries over more than 70 seconds without releasing BLE ownership or allowing RF. Repeated controller-shutdown errors have equivalent missing overall recovery bounds.

Add a common bounded recovery deadline or meaningful host heartbeat for scan/host/controller teardown; keep RF physically off until controller recovery is confirmed. Client-only and loop-only monitoring are insufficient.

### P1 — a slow or disrupted POST can exceed the application progress deadline

The pinned [WebServer body reader](https://github.com/espressif/arduino-esp32/blob/3.3.12/libraries/WebServer/src/Parsing.cpp#L45) runs synchronously inside `server.handleClient()`. Its five-second timeout resets between arriving chunks, and Content-Length is not bounded before body allocation. A native reproduction of the actual reader needed 313.6 seconds for a slowly arriving 64-byte body, exceeding the firmware's 70-second loop progress deadline. This can cause a controlled reboot and excessive transient allocation during a poor client/network transfer.

Bound request body size before allocation and impose an absolute header/body budget comfortably below the progress deadline, or use a verified bounded streaming server. Increasing the watchdog alone would hide the responsiveness defect.

### P2 — Bluetooth may send time after clock confidence is lost mid-session

[Entry trust check](https://github.com/whitto/time-transmitter/blob/v4.14-r2/firmware/RadioClock_V4_14/RadioClock_V4_14.ino#L3886) occurs before the connection and optional/required work. [Cancellation](https://github.com/whitto/time-transmitter/blob/v4.14-r2/firmware/RadioClock_V4_14/RadioClock_V4_14.ino#L2796) checks RF demand and transaction duration, but not clock confidence. The final TIME write does not recheck trust. Actual BX function/captured-packet fixtures changed trust to false during the transaction and still acknowledged TIME and returned success.

Cancel active work on lost confidence and check again immediately before sampling/sending final TIME. Retain normal disconnect and callback unwinding; optional battery/font errors remain separate from time delivery.

### P2 — lifetime timer recovery budget can be exhausted by separate healthy episodes

[Recovery service](https://github.com/whitto/time-transmitter/blob/v4.14-r2/firmware/RadioClock_V4_14/RadioClock_V4_14.ino#L1478) caps retries at three per boot and never replenishes them after verified healthy operation. Three isolated stalls, each recovering successfully a week apart, consumed the budget; a fourth transient fault received no attempt and remained latched RF-off. This is the implemented per-boot policy, rather than a hidden unbounded retry loop, but it limits years-long unattended recovery.

Use bounded consecutive-failure/rate-window budgets and replenish only after a sufficiently long verified healthy period. Keep lifetime diagnostic counts separate from the current retry budget.

### P2 — configuration layout bounds do not validate every field or stored content

[Boot parsing](https://github.com/whitto/time-transmitter/blob/v4.14-r2/firmware/RadioClock_V4_14/RadioClock_V4_14.ino#L4143) bounds files/lines, but permissive integer conversion can accept trailing garbage. Actual `loadConfig()` accepted `630junk` as schedule minute 630 without a storage fault. Atomic save/readback protects new writes; it does not validate all later stored contents.

Parse every field strictly into a complete candidate before applying it; add versioned content integrity checking and bounded legacy migration. Retain corrupt records for explicit recovery and avoid new periodic flash writes.

### P2 — failed Wi-Fi shutdown leaves desired and observed states inconsistent

`ntpstop()` ignores failures from `WiFi.disconnect(true)` and `WiFi.mode(WIFI_OFF)` after the caller records Wi-Fi as Off. Injected failures in the actual function left the station connected while HTTP/SNTP were stopped and supervision skipped recovery as an intentional shutdown.

Check transition results, keep desired/observed state separate, expose a RAM fault and use bounded retries/recovery without configuration rewrites.

### P3 — short NTP intervals can prevent uncertainty recovery

[Drift update](https://github.com/whitto/time-transmitter/blob/v4.14-r2/firmware/RadioClock_V4_14/RadioClock_V4_14.ino#L2479) requires at least 300 seconds between replies. A valid 500 ms jitter sample at 300 seconds creates a 3,000 ppm conservative bound and 210-second interval. One hundred subsequent perfect replies at that interval never updated/decayed the bound. Frequent Wi-Fi/NTP wakes can therefore persist until a longer gap or reboot.

Aggregate short-interval measurements or permit conservatively bounded uncertainty updates over them. Preserve the absolute bound and holdover safety checks.

### P3 — SSID length validation exceeds the platform limit

UI/API accept up to 63 bytes, while the pinned ESP32 station API rejects SSIDs over 32 bytes. Reject unsupported byte lengths before committing credentials; account for UTF-8 byte length. The setup AP still permits correction, so this is a configuration validation issue rather than an irreversible lockout.

## Memory, timing and physical limits

No steadily growing application RAM leak was demonstrated. The fixed schedules/profiles/notification buffers, retained BLE client and bounded response/config builders are sound under the reviewed tests. Dense advertisements and SDK/STL/socket/header allocations can still cause pressure outside the checked singleton paths. A stable native heap does not establish stable ESP32 heap fragmentation or sufficient hardware task stacks.

Physical Node32s/watch soak is still required: repeat real scan/connect/disconnect/controller transitions, router/NTP outages, corrupted storage and interrupted config saves, midnight/DST/rollovers and RF recovery. Compare free/minimum/largest-block heap and loop/radio/LED/NimBLE stack minima at equivalent points. Measure real RF boundary timing and reception. Use RAM/serial/external captures, not periodic flash logs.

Prioritise the three P1 recovery/request problems, then final BT trust and replenished timer recovery, before relying on years-long unattended service. These additional findings are reported for a further revision; they are not silently fixed in the published R2 source.

Native reproduction source is retained in [the post-review evidence directory](build-evidence/v4.14-r2/post-review/). Full published-source test, compile and browser logs are beside it. These fixtures deliberately demonstrate remaining failure paths; they are not passing regression assertions for fixed firmware.
