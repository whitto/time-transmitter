# RadioClock V4.8 — Wi-Fi setup recovery and Settings

Active source: `firmware/RadioClock_V4_8/RadioClock_V4_8.ino`. Build target: classic ESP32, `esp32:esp32@3.3.12`, NimBLE-Arduino 2.5.1, ArduinoJson 6.21.5, 4 MB flash / Huge APP (No OTA).

## Reported NTP issue

A device without saved credentials starts in setup/AP mode. In V4.7, saving Wi-Fi credentials switches the hardware into STA mode and starts association but leaves `ap_mode` set. Wi-Fi supervision and scheduled power management then skip their work. The station can obtain an IP and serve the UI while SNTP was never configured. Restarting an uninitialized SNTP client from the web UI does not initialize it.

V4.8 fixes the setup-to-station transition and initializes SNTP after station connection. Setup access remains available while new credentials connect; failed credentials return to setup. A manual NTP request starts the client if needed. Setup SSIDs use the active AP interface MAC rather than reading an inactive station interface. Confirmed replies emit `NTP synchronized (confirmed server reply)` from the main loop. Clock trust still requires an actual SNTP notification, not simply a plausible date left from holdover.

## UI requests

- **Bluetooth power saving** is in **Settings**, with its saved switch and Always Wait interaction preserved. Wi-Fi configuration and Wi-Fi power remain in Network.
- The queued success wording is applied: **Last watch result** and the overview watch result show **Time sync delivered** for acknowledged writes. Failure messages and the last successful date/time remain distinct. Diagnostics retains the precise delivery evidence and its display-verification limitation.
- The approved left sidebar and eight navigation labels remain intact.

All 16 Python host tests, UI handler/browser regressions, 10,000-session RF arbitration stress, five viewport widths and both themes passed. The generated image checksum and validation hash are valid. Independent Wi-Fi/NTP review passed. Release evidence is recorded in `build-evidence/v4.8`. Host regressions exercise actual Wi-Fi/NTP functions with setup success/failure, reconnect, SNTP startup/restart and notification handling. UI/browser checks cover the power card placement, persistence/rollback, success/failure wording and existing controls. Rendered Settings, Network, Watch and overview pages are reviewed against the requested layout at desktop/phone widths. Existing clock/encoder and Bluetooth/RF tests remain required.

Physical Wi-Fi/router NTP access and watch/RF operation still require hardware acceptance. UDP/123, DNS and internet availability cannot be tested against the user's Cloud network here. This fixes the demonstrated firmware state bug; it does not diagnose the earlier intermittent boot checksum failures.
