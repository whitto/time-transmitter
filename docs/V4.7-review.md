# RadioClock V4.7 — diagnostics and restart investigation

The active sketch is `firmware/RadioClock_V4_7/RadioClock_V4_7.ino`, targeting `esp32:esp32@3.3.12` with NimBLE-Arduino 2.5.1 and ArduinoJson 6.21.5. Select Huge APP / No OTA for the classic 4 MB ESP32.

## Requested diagnostics

Diagnostics now starts with:

- **Full-time BT listen (Always Wait)**: Off, On with the current Bluetooth phase, or On but paused during RF transmission. Enabled does not imply the watch will initiate a connection.
- **Next JJY transmission**: the next daily JJY 40/60 kHz window's date, start time, station timezone, format and countdown. It excludes other radio formats, rolls to tomorrow when needed, describes active JJY windows and makes full-time RF overrides explicit. It uses saved server schedules rather than unsaved editor drafts; BT timezone and offset do not shift the LF schedule.

## Restart investigation

The previous UI had no in-flight guard for forced Diagnostics refreshes. Repeated navigation/Refresh clicks could issue overlapping refreshes while earlier requests were still pending. Refreshes now share one promise; the diagnostic/status/config/schedule reads execute sequentially. A Chromium regression fires 20 simultaneous refresh calls during navigation and verifies one diagnostic request.

This is a confirmed request-overlap issue, not proof of the reported restart cause. Diagnostics now reports the ESP-IDF last-reset reason, largest contiguous heap allocation and minimum remaining loop-task stack. Boot serial output also prints the reset code. Panic, watchdog and brownout reasons can guide follow-up; a serial backtrace is needed to identify a crashing instruction. No physical restart has been reproduced in this environment.

The diagnostic handler rejects allocation/JSON-overflow failures with HTTP 503 and reserves the response once before serialization. Diagnostic reads and allocation checks do not change RF timing, Bluetooth protocols or scheduler behavior. An exact normalized source comparison against V4.6 allows only version/UI changes, reset logging/include and the diagnostic handler changes.

## Validation

All release checks passed: core 3.3.12 compilation uses 1,404,096 / 3,145,728 bytes flash (44%) and 62,000 / 327,680 bytes RAM (18%). The 15 Python host tests, packet fixtures, UI handler checks, 10,000-session RF arbitration stress and Chromium regressions pass. Build and regression evidence is in `build-evidence/v4.7`. The approved left sidebar and all eight navigation labels are retained. Rendered Diagnostics and overview screens are reviewed; five viewport widths and both themes are checked. Firmware/host tests cover existing clock, encoders, RF arbitration, Bluetooth lifecycle, watch settings, LED and persistence. New UI tests cover listen On/Off/RF pause, JJY-only filtering, next-day rollover, active windows, full-time overrides, unknown clock and repeated refreshes.

Hardware restart stability, RF waveform and physical watch behavior still require device testing. If a restart occurs, capture the serial panic/backtrace and the new reset/memory fields after reboot.
