# RadioClock V4.12 — watch battery reporting

V4.12 reads a battery estimate during GW-BX5600 Bluetooth sync and displays it on **Watch (BLE)** and the overview's top **Watch** card. It preserves the approved sidebar layout, successful time-delivery date/time and existing firmware behavior. Source release only; physical battery acceptance remains a device test.

Active sketch: `firmware/RadioClock_V4_12/RadioClock_V4_12.ino`. Previous release: V4.11, commit `9edbdc2462b76757cabba9ca689e62689c6e93b8`. Dependencies remain **Arduino-ESP32 3.3.12**, **NimBLE-Arduino 2.5.1** and **ArduinoJson 6.21.5**.

## Verified protocol

The GW-BX5600 uses the vendor watch-condition command **0x28**, sent as a single-byte **Write Without Response** on `26eb002c-b012-49a8-b1f8-394fb2032b0f`. Its nine-byte reply arrives on TIME/all-features `26eb002d-b012-49a8-b1f8-394fb2032b0f`, rather than the SP_DATA characteristic. Byte 1 is the raw battery reading. The model-specific calibration is **14–24**: `clamp((raw - 14) * 10, 0, 100)`.

The displayed percentage is an **estimate in 10% steps**, not a direct state-of-charge measurement. The generic 9–19 calibration would give incorrect BX results. Other model protocols remain unavailable until their model/calibration has been validated. No standard Battery Service is assumed.

- [gshock-smart-sync-webapp](https://github.com/izivkov/gshock-smart-sync-webapp), commit `5b3ff83dbae43a7a526232e5f35de98425ca7ac8`: `src/api/WatchInfo.ts` GW-BX5600 calibration and `src/api/io/WatchConditionIO.ts`.
- [gshock_api](https://github.com/izivkov/gshock_api), commit `ae817310dd9551d5e6e53ee61d89af4e8d954767`: `watch_info.py`, `iolib/watch_condition_io.py` and raw Bluetooth captures. The helper is independently implemented; project credits are retained.

Identified GW-BX5600 captures, using zero-based frame numbering:

| Capture | Request / reply | Reply | Estimate |
| --- | --- | --- | --- |
| `btsnoop_hci-bx2.log` | 1224 / 1226 | `281418000000020000` | 60% |
| `btsnoop_hci_bx3_official_app.log` | 722 / 724 | `281821000000020000` | 100% |

The bx2 capture identifies CASIO GW-BX5600 and a lower-right-button manual time request. Its battery reply arrives about **127 ms** after the request, before SP step 1 and final TIME. The official-app example replies in about **143 ms**, also before TIME. The similarly named `btsnoop_hci_bx.log` identifies a GMW-BZ5000; it is not used as BX battery evidence.

## Session behavior and storage

The optional battery read runs before the existing SP/time handshake. Notification reception is armed before the GET write; channel/header, full nine-byte size, overflow and copied size are checked. The **reply wait** is bounded to **1.5 seconds**, including the existing 300 ms fragment-assembly gap. Discovery/subscription are existing guarded synchronous GATT operations and have their own operation time; 1.5 seconds is not an end-to-end session bound. SP/font reply waits retain their five-second default.

A battery-only error does not prevent the required time attempt. A disconnected watch or RF cancellation still stops BLE operations through the existing guards. Optional font work and fresh time sampling retain their order, with TIME sent last.

Readings commit only after a successful TIME write, after any replacement binding is applied. Each profile retains a last-known estimate, sample UTC time and watch address **in RAM only**. A failed read can retain the same watch's previous sample with an error status. A replacement cannot inherit another watch's reading. Reboot clears all readings. This feature adds **no flash writes**; the two existing runtime flash-write reductions remain queued separately.

Each `bt_profiles` object adds nullable `battery_percent`, `battery_read_at` in the selected Bluetooth timezone/offset, and `battery_status`. Both requested cards follow the selected watch profile. A valid **0%** remains distinct from unavailable; the Watch page labels the sample as a last reading.

## Validation

- `bash scripts/test.sh`: **31 Python host cases passed**, plus JavaScript handler checks, captured BX packet checks and 10,000-session concurrent RF/BLE arbiter stress with no modeled overlap.
- Six battery cases exercise captured calibration, exact size/header/channel, fragmented and late notifications, overflow, timeout and millis rollover, cancellation/disconnect, required no-response GET, optional failures preserving SP/TIME, fresh time after optional work, successful-TIME-only commits, profile/replacement isolation and no battery persistence.
- `node scripts/test-ui-browser.cjs`: passed battery values 0/60/100%, null, timestamps, retained readings on failure, profile selection/restart and existing font/power/LED/schedule/pairing regressions. All eight sidebar routes remain.
- Node32s compile: **1,411,588 / 2,097,152 bytes (67%)** program storage; **62,272 / 327,680 bytes (19%)** global RAM, leaving 265,408 bytes. FQBN `esp32:esp32:node32s:PartitionScheme=no_ota,FlashFreq=40`.
- ESP32 image **DIO / 40 MHz / 4 MB**; checksum and validation hash valid. Retained cloud ELF SHA256: `8e6461917ce730a9cabc53c0e07dd5532790b4494562d46a50705870f23201a0`.
- Embedded UI round-trip: **91,105-byte HTML**, **24,127-byte gzip**, 150 unique DOM IDs and nine API routes.
- Rendered overview and Watch pages were inspected against `ui/v32_ui_mockup.png`. The fixed sidebar and existing arrangement remain; only a battery line and reading rows/status are added. Successful sync date/time remains visible.
- Normalized source comparison: Wi-Fi/NTP, RF timing/encoders/schedules, timezones, configuration format, scan coordinator, arbiter, font/SP packet helpers and partitions are unchanged. Battery code/notification routing, parameterized reply wait, profile status JSON, version metadata and UI additions form the firmware scope.

Evidence: [build-evidence/v4.12](build-evidence/v4.12), including compiler and host/browser logs, image validation, source hashes, scoped firmware diff and rendered screenshots.
